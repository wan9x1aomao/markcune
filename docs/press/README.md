# 新闻稿怎么写、怎么更

对外发布一个版本，就有一篇新闻稿。这份文档是规则，稿子本身放在同目录的 `<版本号>.md`。

## 什么时候写

- **每个对外版本（x.y.z）写一篇**，和发版同一天，发版前定稿。
- 补丁版本如果只是修复、没有用户能感知的新东西，可以并进上一个版本的稿子，在「这一版还包含」里补一行；有可见的新功能就必须单独写。
- 新闻稿是**发版的一部分**，不是发版之后补的作业。版本号变了、稿子没变，等于没发。

## 文件放哪

```
docs/press/
  3.5.2.md      ← 一个版本一篇
  3.5.0.md
  README.md     ← 就是这份规则
```

- 文件名必须和 `package.json` 里的 `version` 完全一致。
- 旧版本不要删，新闻中心靠它归档。
- 稿子里的日期用发布当天（Asia/Shanghai）。

## 一版稿子的结构（按顺序，别乱）

1. **标题**：`MDPad <版本> 发布：<这一版最值得说的一件事>`，不超过 30 字
2. **副标题**：一行，说清定位与边界（体积 / 价格 / 许可 / 账号）
3. **导语**：日期 + 版本 + 这一版新增什么，一段话说清
4. **这一版**：只写用户能感知的变化，从 `CHANGELOG.md` 挑 3–4 条，用人的话重写
5. **背景**：产品要解决的问题，基本不变
6. **产品**：平台、体积、功能，基本不变
7. **AI 原则**：只提建议、采纳才落笔、Key 在本机、不中转，规则没变就不动
8. **引语**：作者原话，一版最多一句
9. **许可**：MIT、源码地址
10. **事实表**：版本 / 平台 / 安装包 / 价格 / 许可 / 网址 / 源码
11. **关于 MDPad**：固定的一段
12. **媒体联系**：邮箱

## 事实从哪里查（不许凭记忆写）

```sh
# 版本号：以 package.json 为准
grep -m1 '"version"' package.json
grep -m1 '"version"' src-tauri/tauri.conf.json

# 已发布的版本与日期
cat ../mdpad-site/latest.json

# 安装包体积：按真实文件算，四舍五入到 0.1 MB
ls -lh ../mdpad-site/downloads/
```

- **体积按文件写**，不要写「每个平台都不到 8 MB」这种概括句——AppImage 因为内置 WebKitGTK 是 81 MB，一写就错。
- 版本号在标题、导语、事实表里必须一致，且等于 `package.json`。
- 平台要求只写真实门槛（macOS 13+ / Windows 10+ / WebKitGTK 4.1），不写「支持所有系统」。

## 写作规则

- **只写能验证的事实**：版本、体积、平台、许可、价格、功能。不写「最好用」「最快」「领先」。
- **不点竞品的名字**。需要对比时写类别：「专业的 Markdown 编辑器大多收费」。
- **引语只能是作者本人说过的话**。没有就不写，别代写——记者会核对，读者也读得出来。
- 一段不超过 4 行；中文标点；数字与英文之间留空格。
- 不写公司愿景，写这一版做完了什么。

## 发布前检查（5 条，逐条打勾）

1. 标题/导语/事实表里的版本号一致，且等于 `package.json`
2. 体积和 `downloads/` 里的实际文件一致
3. 引语是作者原话（或已删除）
4. 媒体联系邮箱能收信
5. 官网 `/press`、`sitemap.xml`、`llms.txt` 都加了这一篇

## 发到哪

- **官网 `/press`**：唯一正本，带日期、`NewsArticle` 结构化数据、`canonical`
- **`llms.txt`**：加一行链接，方便 AI 抓取
- **`sitemap.xml`**：加一条
- **媒体资料包**：Logo、App 图标、界面截图、这一篇的 Markdown

## 和发版脚本的关系

`scripts/release.sh <版本号> "更新说明"` 跑完代表**代码发出去了**，不代表**对外说完了**。

建议顺序：

1. 跑 `scripts/release.sh`
2. 按本文档写 `docs/press/<版本号>.md`
3. 更新官网 `/press`、`llms.txt`、`sitemap.xml`
4. 再往外发（媒体、社交平台）

以后可以给 `release.sh` 加一行非阻塞检查：`docs/press/<版本号>.md` 不存在就提醒一句。
